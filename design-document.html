Section 1

Component Overview

This component delivers a sample 3rd party UI Lightning Web Component (LWC) — customProductHeader — that can be added to the Salesforce Revenue Cloud Advanced (RCA) Product Configurator. It allows sales reps to view and edit custom Quote Line Item fields directly inside the Configurator UI, without leaving the configuration experience.

The benefit of introducing a 3rd party UI component is that:

  • It allows the customer to extend the Configurator UI without fully replacing it, preserving the standard Revenue Cloud data pipeline.
  • It helps prevent putting quote line level information into the attribute model, which would create unnecessary complexity in product design.
Best Practice Advisory

Before introducing any third-party LWC customization, the recommended approach is to work with the customer to evaluate and accept the out-of-the-box (OOTB) first-party configurator behavior.

This type of third-party component should only be introduced when both of the following conditions are true:
  • The business requirement cannot be fully met by OOTB configurator behavior, and the only customization required is a component that allows the sales rep to update a field directly on the quote line item; and
  • Modelling the requirement as a product attribute would result in bad product design — for example, forcing operational or transactional data into the attribute layer which raises the level of effort for integration or other customization.

Introducing custom LWC components increases long-term maintenance cost and can be impacted by future Revenue Cloud upgrades. Always document the business justification for choosing this approach.

What This Component Does Not Do

The following are known gaps in the current implementation. They are intentionally left out of this sample but should be addressed before using this component in a production project.

1 — Quote Line Item data is not loaded as initial values (wire not functional)

Although the code includes a @wire(getRecord, ...) block that is intended to fetch the current Quote Line Item field values and populate the inputs when the component loads or when the user navigates to a different line, this wiring is not currently working. The inputs will always start empty regardless of what is saved on the record. The wire code block exists in the codebase as a reference implementation only.

In a real client project, the wiring must be validated and fixed so that the component reflects the current saved state of the record when the configurator opens. Without this, a sales rep editing a field would have no visibility into the previously saved value, creating a risk of unintentional overwrites.
2 — No LMS publish locking / debounce guard

When an LMS valueChanged message is published to the Product Configurator Data Manager, the first-party configurator enters a brief processing state (spinner) while it applies the change. If a second LMS message is published before the first has finished processing, the Data Manager will throw an error.

This component has no protection against rapid or concurrent LMS publishes. In a real client project, consider implementing one or both of the following safeguards:
  • Locking: Set a boolean flag (e.g. _isPublishing) to true when a publish starts and disable all Save buttons until the Data Manager confirms the operation is complete (via an incoming LMS event).
  • Debouncing: Introduce a short delay (e.g. 300–500 ms) before firing the publish, cancelling any pending publish if the user triggers another save within that window.

Installation & Deployment

Prerequisites

🛠

Salesforce CLI

Install the SF CLI: npm install -g @salesforce/cli. Verify with sf --version.

🔐

Authenticated Org

Log in with: sf org login web --alias myOrg. The org must have Revenue Cloud Advanced enabled.

📦

Node.js

Node.js 18+ required for local dev tooling (npm install in the project root).

Step-by-Step: Full Deployment

  • Clone / obtain the project

    Ensure the ThirdPartyConfig SFDX project folder is on your machine and you are in its root directory.

    cd ThirdPartyConfig

  • Authenticate to the target org

    sf org login web --alias targetOrg --set-default

  • Deploy everything via the full manifest

    The manifest/lwc.xml package includes the LWC, all 7 custom fields, Admin profile permissions, the Flow, and the Apex class. Deploy order is managed automatically by the Metadata API.

    sf project deploy start --manifest manifest/lwc.xml
    On success you will see Deploy Succeeded with a summary of all deployed components.

  • Verify the deployment

    # List recently deployed metadata
sf project deploy report

# Or open the org and check Setup → Custom Fields on QuoteLineItem
sf org open --target-org targetOrg

  • Add the component to the configurator flow screen

    In Flow Builder, open RCA Custom Configuration Flow (or your custom clone of it), edit the S01_ProductConfiguratorUI screen, and drag Custom UI Component from the Components panel onto the canvas. Map the input properties as shown in Section 2.

Section 6

Context Definition Setup

The Product Configurator uses a Context Definition to map Salesforce record fields into the configurator's runtime context. To make the 7 new custom fields available within the configurator (for pricing procedures, constraint rules, etc.), you must update the Context Definition in your org.

Important: Context Definition configuration is done entirely through the Salesforce UI in Setup — it cannot be deployed via metadata. Complete these steps after the metadata deployment in Section 5.

Understanding the Context Architecture

ConceptDescription
Context DefinitionA metadata-driven structure defining what data is loaded into the runtime context. Think of it as the schema for the configurator's "working memory".
NodeA container mapped to a Salesforce object (e.g. SalesTransactionItem → QuoteLineItem).
AttributeA single field within a node, mapped to a specific object field API name.
Context MappingDefines how the context is hydrated (populated) at runtime — links nodes to actual record IDs.

Steps to Add Custom Fields to the Context Definition

  • Navigate to Context Definitions

    From Setup, search for Context Definitions in the Quick Find box and open it. Locate the active Context Definition used by your configurator (typically named something like Product Configurator Context or Sales Transaction Context).

  • Open the SalesTransactionItem node

    Inside the Context Definition, find the node that maps to QuoteLineItem. This is typically named SalesTransactionItem. Click to open it.

  • Add Attributes for each custom field

    For each of the 7 custom fields, click New Attribute and fill in:

    Attribute NameField API NameData Type
    Special NotesSpecial_Notes__cString
    Apply ContingencyApply_Contingency__cBoolean
    Target MarginTarget_Margin__cDouble
    Target PriceTarget_Price__cDouble
    Estimated Delivery DateEstimated_Delivery_Date__cDate
    Hierarchy LevelHierarchy_Level__cDouble
    Preferred Delivery HourPreferredDeliveryHour__cString

  • Save and activate the Context Definition

    After adding all attributes, click Save. If the definition requires activation, set its status to Active. Inactive context definitions will not hydrate data at runtime.

    Once active, the configurator will include the custom field values in the runtime context on every page load.

  • Assign Context Tags so that the attributes are accessible via LMS

    Create Context Tags that alias the new attributes. Note: tags don't need to match the field API name. When referencing from LMS, use the tag name, not the field API name instead of the field name

  • Verify in a test configuration

    Open a Quote, launch the Product Configurator, and configure a product. Use browser developer tools (Console → Network) or the Apex Context.IndustriesContext.queryTags() API to confirm the new attributes appear in the context payload with correct values.
